imgx

Batch image processor: resize, rename, convert format, and strip EXIF — non-destructively.

Overview

imgx is a command-line tool written in Go that takes a folder of images and produces a processed copy of each image in an output folder. The originals are never modified.

A single invocation can do any subset of:

  • Resize to a target width, height, or fit-within bounding box (aspect ratio preserved; never upscales in fit mode).
  • Rename to a sanitized, ASCII base name followed by a sequential index — or keep each file's original sanitized name with --keep-names.
  • Convert format between JPEG, PNG, GIF, WebP, AVIF, and TIFF. HEIC and HEIF inputs are decoded and transcoded (decode-only).
  • Strip EXIF metadata — location, camera make/model, timestamps, etc.

imgx is designed to be invoked ad-hoc from a terminal, driven by a config file, or run as a Docker container against bind-mounted input and output directories.

Quick start

The fastest path, assuming Docker Desktop is running:

Option 1 — HTTP UI (default)

# 1. Build and start the server (first build takes ~2 min)
$ docker compose up --build

# 2. Open the upload form in your browser
$ open http://localhost:8080

Drop images (or a ZIP of images) into the form, pick naming / resize / format / quality / sort, submit, and the browser downloads a ZIP containing the processed files.

Option 2 — CLI batch (opt-in profile)

# 1. Drop images into ./input
$ mkdir -p input output
$ cp ~/my-photos/*.jpg ./input/

# 2. Run a one-shot batch through the imgx-cli service
$ docker compose --profile cli run --rm imgx-cli \
    --out /data/output --width 1200 --format jpg /data/input

# 3. Look in ./output
$ ls output/
input-1.jpg  input-2.jpg  input-3.jpg  ...

The cli profile is required so that docker compose up does not try to start a batch run alongside the server.

Configurable host port The server binds to 8080 inside the container and maps to ${IMGX_PORT:-8080} on the host. Copy .env.example to .env to change the host port or bind interface — see Environment variables.

Installation

Option A — Docker (recommended, no Go toolchain required)

Requires: Docker 20+ with Compose v2. Everything else (Go toolchain, dependencies) lives inside the container.

$ git clone https://github.com/<your-org>/imgx.git
$ cd imgx
$ docker compose build          # ~2 min on first build

Option B — From source

Requires: Go 1.27+.

$ git clone https://github.com/<your-org>/imgx.git
$ cd imgx
$ go build -o imgx ./cmd/imgx
$ ./imgx --help
Note go.sum is not committed to the repo. The first go build (or go mod tidy) will generate it locally; the Docker deps stage does the same inside the container.

All flags can be set either on the command line or in a config file (see Config file). CLI flags always override config-file values.

Config file

imgx accepts YAML or TOML config files. The format is detected by file extension.

Discovery

  1. If --config <path> is passed, that file is loaded verbatim.
  2. Otherwise imgx looks for imgx.yaml (or imgx.toml) in the current directory, then in ./configs/.
  3. If no config is found, only flags and environment variables are used.

YAML example

input: ./photos
out: ./out
name: my-images
width: 1200
format: jpg
quality: 85
sort: alpha
recursive: true
concurrency: 4
# fit: 1200x1200         # mutually exclusive with width/height
# height: 800
# dry-run: false
# verbose: false

TOML example

input       = "./photos"
out         = "./out"
name        = "my-images"
width       = 1200
format      = "jpg"
quality     = 85
sort        = "alpha"
recursive   = true
concurrency = 4

Every key in the config file has the same name as its CLI flag (without the leading --). Dashes are preserved: use dry-run: true, not dry_run.

Precedence rules

When a value is set in more than one place, the later source wins:

  1. Config file — lowest precedence.
  2. Environment variables prefixed IMGX_ (e.g. IMGX_WIDTH=1600).
  3. Command-line flags — highest precedence.

The positional <input-dir> argument, if given, overrides the input: field in the config file.

Validation imgx validates the merged config after all sources are applied. Errors (e.g. two resize modes set simultaneously, --quality outside 1–100) produce a non-zero exit code before any image is read.

Supported formats

FormatReadWriteNotes
JPEGyesyesQuality controlled by --quality. JPEG has no alpha channel, so alpha-bearing sources (e.g. transparent PNG) are flattened onto a white background before encoding — matches Photoshop / browser defaults. Go's stdlib would otherwise composite against black, producing dark halos around transparent logos.
PNGyesyesLossless; --quality is ignored.
GIFyesyesOnly the first frame of animated GIFs is written.
WebPyeslosslessPure-Go encoder is lossless; --quality is ignored.
TIFFyesyesWritten with Deflate compression.
BMPyesnoRead-only — convert by passing --format.
AVIFyesyesVia libheif + aom (AV1). Quality controlled by --quality. Requires the heif build tag.
HEIC / HEIFyesnoDecode-only (brands: heic, heix, mif1, msf1). Convert to AVIF/JPEG/PNG/WebP via --format. Requires the heif build tag.

Format is detected by magic bytes, not by file extension. A file named photo.jpg that is actually a PNG will be correctly identified as a PNG.

The heif build tag HEIC and AVIF support is gated behind the heif build tag because it pulls in libheif (C library) via CGO. The Dockerfile always passes -tags heif so the published image has full HEIF/AVIF support. Local go build/go test without the tag still compiles — HEIC/AVIF inputs will fail with "image: unknown format" and --format avif returns a clear error. Pass -tags heif locally once you have libheif-dev libaom-dev libde265-dev installed.

Processing pipeline

Each image that the scanner finds is processed through the following steps, in order, by a worker goroutine:

Read ─▶ Decode ─▶ Resize ─▶ Convert ─▶ Strip EXIF ─▶ Encode ─▶ Write
 │        │         │         │           │            │        │
 │        │         │         │           │            │        └── atomic: write to .tmp, then rename
 │        │         │         │           │            └────── target format (opts.quality for JPEG)
 │        │         │         │           └─────── re-encode from image.Image drops all metadata
 │        │         │         └──────── choose output format (--format) or keep source
 │        │         └────── width / height / fit (skipped if no resize flag)
 │        └────── registered decoders: JPEG, PNG, GIF, WebP, TIFF, BMP (+HEIC, AVIF with -tags heif)
 └────── file opened in streaming mode; magic bytes already verified by scanner

Why EXIF is stripped "for free"

imgx re-encodes every output by first decoding the source into a raw image.Image (pixel grid), then encoding those pixels with a fresh writer. EXIF lives outside the pixel grid — in JPEG APP1 segments, PNG text chunks, TIFF IFDs — and is simply never carried forward. There is no explicit "remove EXIF" step.

Alpha handling at encode time

PNG, WebP, AVIF, and TIFF outputs carry the source alpha channel through unchanged. GIF preserves single-colour transparency. JPEG has no alpha, so when the encoder sees an alpha-bearing source type (*image.RGBA, *image.NRGBA, or the 64-bit variants) imgx first draws it onto a white canvas (draw.Over) and hands that to the JPEG encoder. The result: a transparent PNG logo encoded to JPEG comes out on white, not Go's stdlib default of black. Opaque sources (YCbCr from an existing JPEG, *image.Gray) skip the flatten entirely.

Output naming

Output files are named <base>-<n>.<ext> where:

<base>
Derived from --name (or the input directory name if --name is not given), then cleaned through transliteration and sanitization.
<n>
A 1-based integer index assigned in sort order (see --sort). Index 1 goes to the first image in the sorted scan, 2 to the second, etc. The index is assigned before workers dispatch, so parallel execution does not change filenames.
<ext>
The canonical extension of the output format: jpg, png, gif, webp, avif, tiff.

Keeping original names

With --keep-names (or the Keep original file names checkbox in the web form), the sequential scheme is skipped: each output keeps its input's file name stem, run through the same transliteration and sanitization stages below, and only the extension changes with the output format (My Photo.PNG → my-photo.jpg when converting to JPEG). --name is ignored in this mode. If two inputs clean to the same stem (or the name is already taken in the output directory), -1, -2, ... suffixes are appended.

Transliteration and sanitization

The raw base name is passed through two stages:

Stage 1 — Translit

  1. ASCII characters pass through unchanged.
  2. Cyrillic characters are mapped using a hand-built BGN/PCGN table (the US/UK standard for romanizing Cyrillic place names — the same used on passports and atlases).
  3. All other non-ASCII characters (Greek, accented Latin, CJK, Arabic, …) fall back to go-unidecode.

Examples:

InputAfter Translit
ПловдивPlovdiv
ЩукаShchuka
Йошкар-ОлаYoshkar-Ola
ЖёлтыйZhyoltyy
überuber
αβγabg

Stage 2 — Sanitize

  1. Lowercase the whole string.
  2. Any character not in [a-z0-9.-] is replaced with -.
  3. Consecutive - are collapsed to a single -.
  4. Leading and trailing - and . are trimmed.
  5. Empty result falls back to the literal string image.

Putting them together:

Clean("Пловдив фото")     → "plovdiv-foto"
Clean("Йошкар-Ола 2024")  → "yoshkar-ola-2024"
Clean("über cool")        → "uber-cool"

Conflict resolution

If the computed output path <base>-<n>.<ext> already exists on disk (or has been reserved by a previous worker in the same run), imgx appends a disambiguator:

photos-1.jpg                (normal case)
photos-1-1.jpg              (if photos-1.jpg already exists)
photos-1-2.jpg              (if photos-1.jpg AND photos-1-1.jpg exist)

Each successful Resolve call reserves the returned name so that no other worker can pick it — avoiding a race where two goroutines both Stat the same path, both see "not found", and both try to write to it.

Concurrency model

imgx processes images in parallel using goroutines inside a single process. It does not fork or spawn child processes.

                                  ┌── worker 1 ─┐
main goroutine ── [job channel] ──┼── worker 2 ─┤── writes to output/
                                  ├── worker 3 ─┤
                                  └── worker N ─┘    (N = --concurrency)
  • A fixed-size worker pool of N = --concurrency goroutines is spawned once. Default is runtime.NumCPU().
  • Each worker pulls one job at a time from an unbuffered channel. A job is a single image plus its pre-assigned index.
  • The pool caps the amount of work in flight. On a 10,000-image folder you are not holding 10,000 decoded images in RAM at once — only N.
  • Output-index assignment happens before jobs enter the channel, so filenames are deterministic regardless of scheduling.
Tuning tip The default (one worker per core) is a reasonable starting point, but decoding large JPEGs is memory-heavy. If you are processing multi-megapixel 24-bit images on a 16-core box, consider dropping --concurrency to half your core count to stay under available RAM.

Error handling

ConditionBehaviour
Input directory does not existFatal — exit code 1 with error message, no images processed.
Output directory does not existCreated automatically (mkdir -p).
Invalid flag combination (e.g. --width + --fit)Fatal — config validation fails before processing.
Individual file fails to decodeLogged as a warning, skipped, run continues.
Individual file fails to encode or writeSame — warning, skip, continue.
Unsupported file type in input dir (e.g. .txt)Silently skipped by the magic-byte scanner.
--format heic requestedFatal — HEIC is decode-only. Use --format avif (or jpg/png/webp) for HEIF-family output.
HEIC/AVIF file encountered in a non-heif buildDecode fails with "image: unknown format"; logged and counted as a per-file error.

At the end of a run, imgx prints a summary line:

Processed: 42  Errors: 1  Elapsed: 2.3s  Dry-run: false  (avg 54ms/image)

When any file failed, a consolidated Failed block is written to stderr before the summary line, listing each input base name and its reason — so you don't have to scroll through interleaved warn: lines:

# stderr
Failed (2):
  IMG_4825.HEIC: no encoder for source format heic; pass --format to convert
  IMG_4826.HEIC: no encoder for source format heic; pass --format to convert

# stdout
Processed: 0  Errors: 2  Elapsed: 12ms  Dry-run: false

If any per-file error occurred, imgx exits with code 2 so the calling shell can branch on $?.

Running in production

The production container is built on gcr.io/distroless/cc-debian13:nonroot — no shell, no package manager, runs as UID 65532. It carries the imgx binary plus the libheif runtime stack (libheif, libde265, libaom/libdav1d) and the libheif codec plugins (libde265 for HEVC decode, aomdec/aomenc for AVIF) needed for HEIC decode and AVIF encode/decode. libx265 is intentionally not shipped (GPL; only HEVC decode is needed for HEIC input). Final image is ~50–60 MB (up from ~7 MB when the build was CGO-free).

The same image powers two compose services:

One-shot CLI batch runs

The imgx-cli service sits behind the cli profile so it never starts implicitly, but stays available for batch processing:

$ docker compose --profile cli run --rm imgx-cli \
    --out /data/output \
    --fit 800x800 \
    --format webp \
    --recursive \
    /data/input

Because ENTRYPOINT is still /imgx, any flags you pass are appended to the binary. The default CMD (serve …) is overridden by the compose service's empty command: [], so CLI args land exactly where you'd expect.

Volume mounts

Only the imgx-cli service mounts bind paths; the server is stateless by design and receives uploads in-memory/temp only.

ServiceHost pathContainer pathMode
imgxnone — stateless HTTP service
imgx-cli./input/data/inputread-only
imgx-cli./output/data/outputread-write

The ./input bind mount is read-only as a safety measure — imgx never writes to its input, and the kernel enforces it.

Running in development (hot reload)

The dev container runs Air, which watches the source tree inside the container and rebuilds + reruns imgx whenever a .go, .yaml, or .toml file changes.

$ docker compose -f docker-compose.dev.yml up --build

The dev compose file bind-mounts the entire repo into /app:

volumes:
  - .:/app                      # live source tree (watched by Air)
  - ./input:/data/input:ro
  - ./output:/data/output

Air configuration lives in .air.toml at the repo root:

[build]
  cmd         = "go mod tidy && go build -tags heif -o ./tmp/imgx ./cmd/imgx"
  bin         = "./tmp/imgx"
  full_bin    = "./tmp/imgx --help"
  include_ext = ["go", "yaml", "toml"]
  exclude_dir = ["tmp", "output", "input", ".git"]
  delay       = 300

The -tags heif flag matches the production build and requires libheif to be installed inside the dev container (it is — the dev Dockerfile stage apt-installs libheif-dev libaom-dev libde265-dev).

full_bin uses --help so that Air-triggered rebuilds do not re-process your ./input folder every time you save a file. When you want to actually run the tool, override the command:

$ docker compose -f docker-compose.dev.yml run --rm imgx \
    go run ./cmd/imgx --out /data/output --width 800 /data/input

Inside docker container:

$ go run ./cmd/imgx --out ./output -r --fit 2048x2048 --format jpg --verbose ./input

From source (no Docker)

If you have a Go 1.27+ toolchain installed:

$ go build -o imgx ./cmd/imgx

$ ./imgx \
      --out ./out \
      --width 1200 \
      --format jpg \
      --quality 85 \
      ./photos

Processed: 42  Errors: 0  Elapsed: 2.3s  Dry-run: false  (avg 54ms/image)

Without the heif build tag (default), the binary has no CGO dependencies and HEIC/AVIF are disabled. To get HEIF/AVIF locally, install libheif-dev libaom-dev libde265-dev and build with -tags heif:

$ go build -tags heif -o imgx ./cmd/imgx

HTTP UI (imgx serve)

imgx ships an optional HTTP server, exposed as a subcommand of the same binary. It serves a minimal upload form at /, runs uploads — individual images or ZIP archives of images — through the same pipeline the CLI uses, and streams the processed batch back as a ZIP download.

$ imgx serve
imgx: listening on http://127.0.0.1:8080

Open the printed URL in a browser, pick one or more images (or a ZIP of images), select naming / resize / format / quality / sort options, and submit. The browser downloads a ZIP containing processed files named <base>-<n>.<ext> — same naming convention as the CLI — or the original sanitized names when Keep original file names is checked.

Flags

--addr <host:port>
Default: 127.0.0.1:8080.
Listen address. Loopback-only by default because there is no authentication. To expose on all interfaces (e.g. inside a container), pass --addr 0.0.0.0:8080.
--max-file-size <bytes>
Default: 52428800 (50 MiB).
Maximum size per uploaded file. Also applies to each entry inside an uploaded ZIP, measured uncompressed (and the archive itself must fit as an upload). Exceeding this returns HTTP 413 with a message naming the offending file.
--max-files <int>
Default: 100.
Maximum number of files per request. Images extracted from uploaded ZIPs count toward the same limit. Exceeding this returns HTTP 413.
--shutdown-timeout <duration>
Default: 30s.
How long to wait for in-flight requests on SIGINT / SIGTERM. New connections are refused immediately; existing requests get this long to finish before being cancelled.

Routes

Method + PathPurpose
GET /Renders the single-page upload form.
POST /processMultipart upload handler; parts may be images or ZIP archives of images (expanded server-side). Response: Content-Type: application/zip with a timestamped filename in Content-Disposition.
GET /healthzReturns 200 "ok". For container health checks.

How uploads are handled

  1. The request body is capped at --max-file-size × --max-files via http.MaxBytesReader.
  2. After ParseMultipartForm, per-file size and total file count are re-checked.
  3. Each part is sniffed by magic bytes. ZIP parts (PK signature) are expanded in place: every entry is sniffed too, images flow through the same sanitise/dedupe naming as direct uploads, non-image entries are skipped (logged and reported in errors.txt), and OS metadata (__MACOSX/, ._*, .DS_Store, Thumbs.db) is dropped silently. Per-entry uncompressed size and the running file count are enforced against --max-file-size / --max-files (413 on violation); a corrupt archive returns 400. Non-image direct parts are likewise skipped and reported.
  4. Surviving uploads' filenames are sanitised (filepath.Base + naming.Clean) and the bodies are written into a fresh os.MkdirTemp input directory.
  5. A config.Config is built from the form fields and passed through the same config.Validate the CLI uses.
  6. Preflight. When the user picks Keep original (empty format), the scanned entries are checked against format.CanEncode. Any read-only format (HEIC, BMP) short-circuits the request with HTTP 400 and a message naming the offending files and the writable formats — catching the "silent drop" trap where all files would otherwise fail the same way at encode time.
  7. scanner.Scan (magic-byte detection) and pipeline.Run process the temp directory into a temp output directory — same worker pool, same deterministic indexing.
  8. On partial failure (some files succeeded, some didn't) or when uploads/zip entries were skipped as non-images, an errors.txt manifest is written into the output dir listing each one and its reason, so the user sees dropped inputs without having to read server logs; the count is also exposed in an X-Imgx-Failed response header that the form surfaces as an inline warning.
  9. The output directory is walked and its files streamed into an archive/zip response (Store, no compression — images are already compressed).
  10. Both temp directories are removed via defer before the handler returns.
Client-side guard The upload form's JS watches for HEIC/HEIF/BMP filenames. When one is present and Keep original is selected, the dropdown auto-switches to JPEG and an inline note ("N file(s) are HEIC/BMP (decode-only) — output set to JPEG.") appears under the format selector. HEIC/BMP files hidden inside an uploaded ZIP bypass this filename watcher — for those, the server-side "Keep original" preflight 400 is the guard, and its message renders inline under the form.
Stateless by design Nothing is persisted between requests. Uploads live only in per-request temp directories and are deleted once the ZIP has been streamed.

Graceful shutdown

The serve command attaches signal.NotifyContext to SIGINT and SIGTERM. On either signal the server stops accepting new connections and calls http.Server.Shutdown with --shutdown-timeout. The request context.Context is threaded into pipeline.Run, so workers observe cancellation past the grace window and exit without leaving partial files behind.

Concurrency

Each HTTP request is handled in its own goroutine by net/http, and within a single request pipeline.Run spins up runtime.NumCPU() workers as it does for the CLI. On a busy server, two simultaneous uploads therefore each try to use all cores. If that becomes a problem in your deployment, either scale horizontally or front the server with a reverse proxy that bounds concurrency.

Running under Docker

The HTTP UI is the default under Docker. The prod image's CMD is serve --addr 0.0.0.0:8080, and docker-compose.yml's imgx service publishes the port — so a single command is enough:

$ docker compose up --build

Change the host-side port or bind interface via .env (no compose-file edit required):

$ cp .env.example .env
$ # edit .env → IMGX_PORT=9000, IMGX_BIND=127.0.0.1
$ docker compose up
# now reachable at http://127.0.0.1:9000
No authentication The HTTP surface has no auth. On shared machines set IMGX_BIND=127.0.0.1 in .env to restrict to loopback, or front the container with a reverse proxy that enforces access control before exposing it on a network.

Docker architecture

The Dockerfile has five stages plus an Air helper stage, so the same Dockerfile produces either a dev container with hot reload or a lean production container depending on --target.

┌─────────────────────────────┐
│  Stage 1: deps              │  golang:1.27-trixie + libheif-dev
│  go mod download all        │  ← cached layer; invalidated when go.mod changes
└────────────┬────────────────┘
             │

Plugin architecture gotcha libheif ≥ 1.17 dlopens codec plugins from /usr/lib/x86_64-linux-gnu/libheif/plugins/ at runtime. Examples

Shrink a camera dump for the web

$ imgx --out ./web --width 1600 --format jpg --quality 80 ./dcim

Produce thumbnails, recursive

$ imgx --out ./thumbs --fit 300x300 --format jpg --recursive ./gallery

Strip EXIF only (no resize, keep format)

$ imgx --out ./clean ./sensitive-photos

Convert PNGs to WebP, preserve dimensions

$ imgx --out ./webp --format webp ./screenshots

Convert iPhone HEIC dump to AVIF

$ imgx --out ./avif --format avif --quality 70 ./iphone-photos
# Inputs: IMG_0001.HEIC, IMG_0002.HEIC, …  → ./avif/iphone-photos-1.avif, …

Convert HEIC to JPEG for wider compatibility

$ imgx --out ./jpg --format jpg --quality 85 ./iphone-photos

Dry run a batch and inspect the plan

$ imgx --out ./out --width 800 --format jpg --dry-run --verbose ./photos

[dry-run] ./photos/IMG_0001.jpg -> ./out/photos-1.jpg (142034 bytes)
[dry-run] ./photos/IMG_0002.jpg -> ./out/photos-2.jpg (138441 bytes)
...
Processed: 42  Errors: 0  Elapsed: 180ms  Dry-run: true  (avg 4ms/image)

Use a config file

# imgx.yaml
out: ./out
width: 1200
format: jpg
quality: 90
sort: alpha
recursive: true

$ imgx -c ./imgx.yaml ./photos

Override one config value via CLI

$ imgx -c ./imgx.yaml --quality 70 ./photos

Cyrillic base name with transliteration

$ imgx --out ./out --name "Пловдив фото" ./photos
# → ./out/plovdiv-foto-1.jpg, ./out/plovdiv-foto-2.jpg, ...

Keep original file names

$ imgx --out ./out --keep-names --format jpg ./photos
# "My Photo.PNG" → ./out/my-photo.jpg, "second.png" → ./out/second.jpg

Troubleshooting

"error during connect … docker daemon is not running"

Docker Desktop (or dockerd on Linux) is stopped. Start it and retry.

"unknown revision vX.Y.Z" on first go mod download

One of the dependencies in go.mod is pinned to a version that does not exist. Inside the container (or locally with Go installed), run:

$ go mod tidy

This will pin each dependency to its latest compatible version and regenerate go.sum. Commit both files after.

"input %q is not a directory"

imgx only accepts a directory as its input, not a single file. If you want to process one file, put it in a dedicated directory first:

$ mkdir -p one && cp photo.jpg one/ && imgx --out ./out ./one

"no encoder for source format bmp"

BMP is read-only. Pass --format to convert to a writable format, e.g. --format jpg.

Output dimensions are wrong after --fit

--fit preserves aspect ratio: the output fits inside the bounding box on both axes, so the smaller dimension is often well under the box size. That is by design.

Processing is slower than expected

Check --concurrency (default is NumCPU). If you are inside a Docker container with CPU limits, the reported NumCPU may be higher than what the cgroup actually allocates; pass --concurrency N explicitly.

"image: unknown format" on a valid-looking image

If the file is HEIC or AVIF, your binary was probably built without the heif build tag (the Docker image always has it; local go build without -tags heif omits it). Rebuild with -tags heif after installing libheif-dev libaom-dev libde265-dev, or run inside the Docker image. For any other valid image that fails, check magic bytes against Supported formats.

Known limitations

HEIC is decode-only. imgx reads HEIC/HEIF containers (brands heic, heix, mif1, msf1) and transcodes them to any writable format. It does not write HEIC output — Debian's libheif pulls in libx265 for HEVC encoding, which is GPL and complicates redistribution. Use --format avif for a modern HEIF-family output that goes through the AV1 path (royalty-free) instead.
HEIF/AVIF require the heif build tag. libheif is a C library accessed via CGO. The Docker build always sets -tags heif, so the prod image has full support. A local go build without the tag omits HEIF/AVIF entirely: HEIC/AVIF inputs fail to decode and --format avif returns an error at encode time. Install libheif-dev libaom-dev libde265-dev and pass -tags heif for local development with HEIF.
WebP encoding is lossless only. imgx uses a pure-Go WebP encoder (github.com/HugoSmits86/nativewebp) to avoid a libwebp/CGO dependency. The encoder produces lossless WebP files, so the --quality flag has no effect for WebP output. File sizes will therefore be larger than what a lossy libwebp encoder would produce.
GIF writes only the first frame. Animated GIFs are decoded frame-by-frame but only frame 0 is written to the output. Multi-frame/animated output is out of scope for v1.
BMP is read-only. You can read BMP inputs, but you must pass --format to convert them to a writable format. imgx does not include a BMP encoder.
No GUI, no video, no cloud upload. These are explicitly out of scope for v1.

Environment variables

Two distinct kinds of env var exist in this project — don't confuse them:

Binary flags (IMGX_*)

Any CLI flag can be set via an environment variable prefixed IMGX_ and using the upper-case flag name with dashes replaced by underscores. These are read by the imgx binary itself (via Viper) and sit between config-file values and CLI flags in the precedence order.

VariableEquivalent flag
IMGX_OUT--out
IMGX_NAME--name
IMGX_KEEP_NAMES--keep-names
IMGX_WIDTH--width
IMGX_HEIGHT--height
IMGX_FIT--fit
IMGX_FORMAT--format
IMGX_QUALITY--quality
IMGX_SORT--sort
IMGX_RECURSIVE--recursive
IMGX_DRY_RUN--dry-run
IMGX_VERBOSE--verbose
IMGX_CONCURRENCY--concurrency

Compose interpolation (.env)

Docker Compose auto-loads .env from the project root and substitutes ${VAR} references in docker-compose.yml before starting containers. These vars control the compose file itself (port mapping, bind interface) — they are not passed to the imgx binary.

VariableDefaultEffect
IMGX_PORT8080Host-side port mapped to container port 8080.
IMGX_BIND0.0.0.0Host interface the port is published on. Set to 127.0.0.1 for loopback-only.

A starter .env.example is checked into the repo:

# Copy to `.env` and adjust as needed.
#   cp .env.example .env
IMGX_PORT=8080
IMGX_BIND=0.0.0.0

.env itself is gitignored (.env.example is the template). Since these variables are only consumed by Compose's string interpolation, editing .env does not affect the imgx serve process inside the container — the server always binds to 0.0.0.0:8080 internally, and the host mapping is what changes.
